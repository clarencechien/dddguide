00 · HOW TO READ

這七頁怎麼用

每頁的結構固定：00 跑完會留下什麼 → 三個 Block（實況、助教對話重播、產出檔案、講師註、全幅圖）→ Check-out → 講師手記。灰底的「參考答案」框是教師手冊的傳統：那是我們認為合理的一種答案，不是唯一答案；學員的版本和它不同時，差異就是驗收要問的問題。

互動的部分不需要學員操作，是給講師看「過程」用的：Day 2 的 Event Storming 牆會從一疊亂貼的便利貼，七步走到有命令、政策、聚合候選與樞紐事件的完整牆；Day 3 的邊界圖一層一層畫出五個 context；Day 4 的紅綠重構逐條重播；Day 5 的重送測試與故障 Saga 逐步走；Day 6 那條 14:02 到 18:18 的午後逐步播放到四欄狀態都對。

講師註 · 這份教師版的假設

假設學員是 1–3 年後端工程師、沒有 EV 領域知識、用 Node 或 Python、一台筆電、每天 6 小時、有 Claude Code 當助教。每頁的產出是「全程跑完且沒有偷看 solutions」的合理結果；時間預算是估的，Day 4 與 Day 6 最容易爆，各頁的講師手記有砍法。

02 · METHOD STACK

方法論在七天裡的出場順序

教材的立場：四樣東西不在同一層，所以出場順序是因果，不是口味。沒有被再造過的流程寫進 DDD 只會得到精緻的舊組織圖；沒有領域語言的事件只會得到會飛的 Excel。

03 · ASSESSMENT

驗收的三個層次

  1. 每日 Check-out（`/checkout dayN`）：助教對照 docs/rubric.md 的 DoD 逐交付物打 ✅ / ⚠️ / ❌，列「最少要補」三項。每頁的 Check-out 節有這張表跑完的樣子。
  2. 最終評量：主控台十題閉卷 ≥ 80%，加上七天 rubric 的 0–3 分加權。Day 7 頁有一份 9/10 的評量報告與 rubric 總表。
  3. 一票否決：五份產物裡有系統名稱沒有現場用語、聚合裡有 I/O、OCPP 的字進了 domain、抄 solutions 沒重寫。rubric 的「一票否決」段落是講師最該背起來的四行。

參考答案 · 講師最常問的一題

「學員切出來的 context 和參考解不一樣，算錯嗎？」不算。驗收看的是每條邊界能不能用三個理由之一說明：這個詞兩邊意思不同、生命週期不同、誰要在斷線時活著。四個 context 或六個 context 都可辯護；「一個超級充電平台」不行，因為它沒有回答任何一個問題。Day 3 頁的「可辯護的替代切法」段落列了三種常見變體。

04 · WHAT THE TEACHER MUST BRING

教材沒有、講師要自己帶進教室的東西

  • 真實故事。教材的五位角色是寫出來的；講師如果有一個真的值班長打過的那通電話，Day 1 開場講它，訪談會活起來。
  • 學員公司的例子。Day 7 的 takeaway 要對應到學員自己的流程；講師在 Day 1 就先問每個人「你們公司哪一條流程是人在當 API」，Day 7 回收。
  • 對 Event Storming 的判斷。一個人做風暴少了團隊的碰撞，助教能挑「非事實」但挑不出「你們公司其實不是這樣」。講師在 Day 2 下午巡一輪，每人問一張黃貼「這句誰說的」。
  • 砍課的決定。七天變五天怎麼砍在 docs/instructor.md；每頁講師手記有那一天的砍法。時間會爆的是 D4 與 D6，不是 D2。

05 · COLOPHON

這七頁怎麼做出來的

單檔 HTML、無第三方 script、無 storage API，照 imitator 的 STYLE.md v3；chassis 原文貼入，聲部是 1990 年代國立編譯館《教師手冊》的淡粉紅道林紙與審核章的藍綠。原始碼在 repo 的 teacher/src/dayN.body.html，用 node teacher/_shared/build.mjs 組裝；圖是手寫的 inline SVG，每張圖後面附文字版表格。學員版主控台是另一份聲部（銅橙、活頁講義），兩邊刻意長得不一樣，讓人一眼分得出手上拿的是哪一本。

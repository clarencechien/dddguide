OCPP → ChargingACL 防腐層StatusNotification(Faulted) → ChargerFaulted；StartTransaction → StartCharging；transactionId 5567 ↔ S-991OCPP 是樁廠商的協定，沒有一群業務人員跟我們一起改版；1.6J → 2.0.1 時 StartTransaction 會消失。做成 Conformist：StatusNotification 滲進 src/charging/domain，升版時聚合要改，老陳的 SQL 也會跟著壞（大泥球第二週）。
Parking ↔ ChargingPartnership 伙伴 + 事件互訂ChargingBayOccupied → Charging；charging.session.started.v1 → Parking（看板）兩邊都在場站、都碰車位、都要在斷線時活；「車位有車」與「槍在充」要對得上但誰都不主宰誰。改成 Parking 單向餵事件：阿忠的看板不知道「這把槍現在有沒有在充」，T1「占用等同充電已開始」的耦合回來。
Charging → BillingCustomer–Suppliercharging.session.started.v1、charging.session.completed.v1（energyWh 12400）上游事件是契約；老陳可以要求 energyWh 用整數（老陳隱藏事實 5），但不能要求 Stop 等他算完。讓 Billing 回呼鎖會話：老陳月底跑批時 Billing 慢，14:31 的 Stop 卡住，車主拔不了槍、阿忠放不了行，§1.1 斷線存活破功。
Parking → BillingCustomer–Supplierparking.session.closed.v1（durationMin、releaseMode=Manual）人工放行後帳務事後對齊（R6）；放行 ≠ 結清。放行要等帳務確認：斷線時閘門開不了，回到阿忠拿鑰匙的 As-Is。
Charging → AssetOpsConformist 遵奉者charging.charger.faulted.v1（chargerId、faultCode、stillEnergized、occurredAt）ChargerFaulted 本來就是業務語言（「設備已聲明無法按契約供電」），AssetOps 翻譯它沒有價值；SLA 直接用 occurredAt 起算（Vicky 隱藏事實 2）。AssetOps 再做一層 ACL：多一份對照表要維護，faultCode 兩邊各自演化，阿豪拿到的故障碼跟小美看到的對不上。
AssetOps → Dispatch內部（Customer–Supplier）ops.work_order.opened.v1（MVP1 程序內呼叫 requestTechnician，固定回 TECH-HAO）同在總部，工單先於派工；備品依故障碼決定（Vicky 隱藏事實 3）。把「技術員已出發」也發給 Billing：帳務被通知淹沒（Vicky 隱藏事實 4）。

6. 不准出現的關係

  • Billing → Charging 回呼（凍結 / 鎖住會話等算錢）：違反 Customer–Supplier 與 §1.1 斷線存活。
  • AssetOps / Dispatch → Billing「技術員已出發」：維修成本不進顧客帳單；帳務只訂閱 session.* 與 parking.session.closed。
  • OCPP 直連任何 domain：StatusNotification、idTag、transactionId 只能出現在 src/adapters/ocpp/。
  • Charging 呼叫總部 API 才能 Start / Stop：授權與計量是場站本機責任；總部只訂閱結果。
  • 任何 Shared Kernel（共用 schema、共用 ORM model）：contracts/*.json 是 Published Language，不是共享核心。
  • Dispatch ↔ Billing 任何直接邊：各走各的。

7. 我推翻過的切法

  • 第一版（白板）：兩堆——場站 / 總部。推翻理由：那是部署位置。「場站」裡阿忠的放行與小美的授權用的詞、守的規則都不一樣；「總部」裡老陳月底才工作，跟 Vicky 每天派工不是同一群人。
  • 第二版（B1 第 40 分鐘）：三堆——場站（停車 + 充電）、維運（工單 + 派工）、帳務。推翻理由：（a）語言衝突 + 生命週期——P-441 14:02–14:33 與 S-991 14:04–14:31 是兩種會話，一對多；（b）一致性——R1 守的是連接器不是車位，「一個車位一輛車」與「一個連接器一個會話」是兩條不變條件；（c）一致性節奏——R5 要在 18:10:08 立刻擋，派工回報要等阿豪從地下室上來；（d）漏掉 OCPP 該放哪——它不是 context，是要被 ACL 隔開的外部協定。
  • 第三版（最終）：五個。保留「三堆」版本的代價紀錄：如果 Sprint 2 Dispatch 仍是 stub，把 AssetOps 與 Dispatch 合成一個 context 是可接受的簡化，但要在 ADR-0001 的替代方案裡留著。

  • Outbox 與 relay 明確存在（R8）；bus 的 redeliver() 是 Day 5 測「同一事件送兩次」用的。
  • Dispatch 是虛線 stub；Parking 是外部系統的事件 stub，不畫內部。

ADR-0001: 以五個 Bounded Context 切分場站與總部

  • 狀態：Accepted
  • 日期：2026-09-17
  • 決策者：學員（工作坊 Day 3）
  • 關聯：workshop/day3/context-map.md、workshop/day3/c4.md、docs/curriculum.md §1.1、§1.4、§1.7

背景（Context）

連鎖停車場營運商在既有停車場（LPR、閘門、月票）新裝 OCPP 充電樁；總部要看全國樁健康度並派工；場站在總部斷線時仍要能進場、充電、人工放行（§1.1）。Day 1 訪談與 Day 2 Event Storming 留下這些事實：

  • 「會話」在阿忠（進場到放行，P-441 14:02–14:33）與小美（授權到結束計量，S-991 14:04–14:31）口中是兩個東西；一個 P-441 可含 0..n 個 S-991。
  • 「狀態」有四個狀態機：OCPP 連接器、充電會話、樁健康、帳單。
  • R1「一個連接器一個進行中會話」與 R5「一根樁一張根因工單」要在命令當下守住；R7「帳單開立後不可改」與合併出帳可以事後對齊（老陳：「晚一點沒關係，不能漏」）。
  • 阿忠隱藏事實 1：斷線時用鑰匙開閘、日誌本記車牌，每月 3–4 次。小美隱藏事實 2：斷線時只有月票卡 24 小時快取白名單能授權。
  • 阿豪隱藏事實 3：地下室無訊號，回到地面才回報，曾被判逾時。Vicky 隱藏事實 4：帳務不該收到「技術員已出發」。
  • 樞紐事件：ChargingStarted、ChargingCompleted、ChargerFaulted。

如果不決定：最可能長成一個 Session 表加 type 欄、status 欄吃四種值，人工放行被未結束的充電會話擋住，OCPP 升 2.0.1 時帳單 SQL 跟著壞（ddd-strategic.md §6 的大泥球六步）。

決策（Decision）

我們把系統切成五個 Bounded Context，各自擁有一套語言、一組不變條件、一個獨立存活條件：

Context不變條件獨立存活
Parking一輛車同一時間一個進行中停車會話總部掛掉仍能開關閘
Charging（核心）一個連接器同一時間一個進行中會話OCPP 在場站；本機授權；總部只訂閱結果
Billing帳單開立後金額不可默默改可延遲出帳，不可丟事件
AssetOps一座樁同一時間一張進行中根因工單總部主系統；場站只上報、保存副本
Dispatch一張工單同一時間一個主責技術員可離線執行，回報後再對齊

Context 間關係：OCPP → Charging 防腐層；Parking ↔ Charging 伙伴 + 事件互訂；Charging / Parking → Billing 顧客—供應者（帳務不得回呼凍結會話）；Charging → AssetOps 遵奉者；AssetOps → Dispatch 內部；AssetOps → Charging 以 ops.work_order.closed.v1 公開語言通知恢復可售。整合一律經整合事件 v1 + Outbox；不用 shared kernel。

替代方案（Alternatives considered）

  1. 兩個 context：場站 / 總部——不選，因為那是部署位置不是語言邊界：「場站」裡放行與授權用不同的詞、守不同規則；「總部」裡老陳月底工作、Vicky 每天派工。它會贏的情況：沒有——它連 R7 都找不到擁有者。
  2. 三個 context：場站（停車 + 充電）/ 維運（工單 + 派工）/ 帳務——這是我 B1 真的用過的切法。不選，因為 P-441 與 S-991 一對多、R1 守的是連接器不是車位、R5 即時去重與派工離線回報節奏不同。它會贏的情況：Dispatch 永遠停在 stub、且 Parking 由廠商系統全權處理時，「維運」合併能少一份契約。
  3. Billing 併入 Charging，Stop 時直接算錢——不選，因為違反「帳務不得回呼凍結會話」與 §1.1 斷線存活；且 Billing 需要「顧客」概念（老陳隱藏事實 1：合併依據是顧客不是車牌），Charging 沒有。它會贏的情況：單一費率、無月票、無車隊、不需要合併停車費——那不是這家公司。
  4. 不做 ACL，直接用 OCPP 名詞——不選，因為 1.6J → 2.0.1 時 StartTransaction 消失，聚合要改；StatusNotification 不是任何利害關係人的語言。它會贏的情況：我們是樁廠商而不是停車場營運商。

後果（Consequences）

  • 正面：R1–R8 每條有唯一擁有者（R1–R4 Charging、R5 AssetOps、R6 Parking、R7 Billing；R8 是各 context 應用層各自守的架構規則）。
  • 正面：場站節點可以只部署 Parking stub + Charging，斷線時完整運作；OCPP 版本升級只影響 src/adapters/ocpp/。
  • 正面：Day 4 起目錄就是 context（src/charging、src/assetops、src/billing），聚合不准 import 其他 context。
  • 負面：Billing 必須自己維護「顧客」與「合併」邏輯，上游不提供；MVP1 只做草稿，合併留 Sprint 2。
  • 負面：R1「連接器是否占用」跨越多個 ChargingSession 聚合，需要 repository 查詢 + 儲存層唯一約束，不能只靠聚合內狀態。
  • 負面：五個 context 的整合事件契約要在 Day 5 前定版，否則 Billing / AssetOps 無法平行開發；多一層 ACL 要維護對照表（阿豪隱藏事實 1 的三套編號）。
  • 負面：場站看板要保存工單副本（訂閱 ops.work_order.opened.v1），場站多一份狀態要對齊。
  • 要監看：Parking ↔ Charging 的 Partnership 在 Sprint 2 真整合時會不會退化成單向；AssetOps 與 Dispatch 若長期都是 stub，考慮回到「合併」並以新 ADR 取代本份。

驗證（How we'll know）

  • grep -rn "StatusNotification\|transactionId\|idTag" src/charging/domain src/billing src/assetops 為空。
  • src/billing 不 import src/charging/domain；沒有任何程式碼從 Billing 呼叫 Charging 的命令。
  • Day 6 斷線劇本：HQ 停掉，site 仍能 Start / Stop / 人工放行；恢復後 outbox 補送。

ADR-0002: MVP1 範圍 = Charging + AssetOps 工單開立 + Billing 草稿帳單

  • 狀態：Accepted
  • 日期：2026-09-17
  • 決策者：學員（工作坊 Day 3）
  • 關聯：ADR-0001、workshop/day3/c4.md（Container 圖）、docs/curriculum.md §1.4（MVP1）、§1.8（契約）、scripts/e2e/e2e.md

背景（Context）

Day 4–6 共三天、一台筆電、Node 或 Python、Docker 選配。ADR-0001 定了五個 context，三天做不完五個。Day 6 要跑通 scripts/e2e 的「14:02 → 18:18」劇本：一次正常充電（S-991，12.4 kWh，草稿 99.2）+ 一次故障開單（WO-2208）+ 一次重複申告（R5）+ 一次 broker 重送（同 eventId）+ 一次修復驗證關單。Charging 是核心子領域；AssetOps 的工單開立是故障流程第一個自動化點（As-Is 的人當 API：阿忠打電話、客服手動開單，平均 20 分鐘）；Billing 是 Charging 事件的第一個消費者，能證明 Outbox + 冪等真的成立。Parking 是既有廠商系統；Dispatch 的路線與備品三天內做不出有意義的版本。

如果不決定範圍：Day 6 最可能做不完的是派工與持久化，而且五個地方都可能壞，E2E 找不到問題在哪。

決策（Decision）

MVP1 實作三塊：

  1. Charging（完整）：ChargingSession 聚合（R1–R4）、StartCharging / StopCharging / ReportMeterValue / ReportFault 命令處理器、OCPP ACL、SQLite 持久化、Outbox relay、HTTP API。
  2. AssetOps（工單開立與關閉）：WorkOrder 聚合（R5）、FaultProcessManager、ops.work_order.opened / closed.v1、關單端點。
  3. Billing（草稿帳單，最小消費者）：訂閱 charging.session.started / completed.v1，以 sessionId 去重，單一費率算草稿金額（12400 Wh → 99.2）；不開立正式帳單、不做 R7、不合併停車費。

MVP1 只做契約與 stub：

  • Parking：parking.vehicle_entered.v1 / parking.session.closed.v1 的 JSON Schema 與範例；ReleaseVehicleManually 端點只發事件（R6 契約成立，不做停車會話聚合）。
  • Dispatch：requestTechnician 固定回 TECH-HAO；不排路線、不預留備品、不做離線 App。

不做清單（明列）

  • Dispatch 真派工：路線、備品預留（Vicky 隱藏事實 3）、離線回報對齊（阿豪隱藏事實 3）→ Sprint 2。
  • Parking 真整合：停車會話聚合、閘門控制、月票資格 → Sprint 2。
  • Billing 合併出帳（停車費 + 電費，依顧客合併）、R7 InvoiceAdjusted、爭議流程 → Sprint 2。
  • 發票開立（Generic，接 SaaS）→ Sprint 2 或更後。
  • 跨時段費率（小美隱藏事實 1：21:50 開始的會話全程算尖峰）→ Sprint 2；契約已含 startedAt / endedAt，不需升版。
  • 真 broker、真 OCPP WebSocket 伺服器、Kubernetes、總部既有系統（客服、ERP）整合。

替代方案（Alternatives considered）

  1. 五個 context 都做薄薄一層——不選：每個都做不深，R1–R5 的 TDD 練習被壓縮，E2E 有五個地方可能壞。它會贏的情況：團隊有五個人、各認一個 context 平行做。
  2. 只做 Charging——不選：沒有消費者就證明不了 Outbox / 冪等 / 契約；故障流程（BPR 主軸、人當 API 最痛的兩點）完全沒落地。它會贏的情況：只剩一天。
  3. Charging + Billing 完整出帳（含 R7、合併）——不選：Billing 需要顧客、費率表、停車事件，三者 MVP1 都沒有；R7 的價值在稽核，不在 E2E 劇本。它會贏的情況：老陳是唯一的贊助者、故障流程不在範圍。
  4. 先做真 broker（Kafka / RabbitMQ）——不選：一台筆電、Docker 選配；in-memory bus 足以證明模式，切換只影響 EventBus adapter。它會贏的情況：MVP1 就要跨兩台機器部署。

後果（Consequences）

  • 正面：E2E 劇本每一步都有真程式碼——進場（stub 事件）→ 充電（真）→ 故障（真）→ 開單（真）→ 派工（stub）→ 關單（真）。
  • 正面：Outbox、冪等消費者、Process Manager 三個模式各有一個真實消費者驗證。
  • 正面：Day 7 的 Sprint 2 backlog 有明確起點：Billing 合併出帳（R7）、Dispatch 路線與備品、Parking 真整合。
  • 負面：草稿帳單用單一費率（8 元/kWh），跨時段計價留 backlog；老陳月底仍要手動合併停車費。
  • 負面：Parking stub 不保證「一輛車一個進行中停車會話」；E2E 劇本不得依賴它。
  • 負面：Dispatch stub 的「指派」不是真派工；ops.work_order.opened.v1 的訂閱者名單在 Sprint 2 會變。
  • 負面：沒有 broker 表示 site 與 HQ 節點 MVP1 實際在同一程序；Container 圖仍畫兩個邊界，README-mvp.md 要註明差異。

Quiz 參考答案

Q1 · 「會話」在阿忠和小美嘴裡不同，是四種線索裡的哪一種？切出哪兩個 context？

語言衝突（同一個詞、不同意思）。阿忠的會話是 ParkingSession P-441（14:02 進場 → 14:33 放行），小美的會話是 ChargingSession S-991（14:04 授權 → 14:31 結束計量）；同一輛 ABC-1234 一個 P-441 可含 0..n 個 S-991。→ Parking 與 Charging。順帶的第二條線索是生命週期：充電結束時停車不一定結束。

Q2 · OCPP → Charging 為什麼是 ACL 而不是 Conformist？做成 Conformist，StatusNotification 會出現在哪裡？

OCPP 是樁廠商的協定，不是任何利害關係人的通用語言，而且它會自己改版（1.6J → 2.0.1 時 StartTransaction 消失）；我們沒有一群業務人員跟它一起演進，所以要翻譯：StatusNotification(Faulted) → ChargerFaulted，transactionId 5567 ↔ S-991。做成 Conformist 的話，StatusNotification、idTag、transactionId 會滲進 src/charging/domain/，之後換 OCPP 版本領域層要跟著改——這正是 rubric 一票否決的第二條。

Q3 · Charging → Billing 是 Customer–Supplier。「帳務不得回呼凍結會話」是什麼意思？違反了會發生什麼？

上游事件是契約：Billing 訂閱 charging.session.completed.v1（energyWh 12400）出草稿帳單，但不能呼叫 Charging 的 API 去「鎖住」S-991 等它算完錢。老陳可以要求 energyWh 用整數（那是對契約的需求），不能要求 Stop 等他。違反了：老陳月底跑批 Billing 慢或掛時，14:31 的 Stop 卡住，車主拔不了槍、阿忠放不了行，§1.1「場站在總部斷線時仍要能充電、放行」破功。

Q4 · Charging → AssetOps 是 Conformist：誰遵奉誰？AssetOps 可以要求 Charging 改事件格式嗎？

AssetOps 遵奉 Charging：接受 ChargerFaulted 的語意與欄位（chargerId、connectorId、faultCode、stillEnergized、occurredAt）原樣進工單，SLA 直接用 occurredAt 起算。它不能要求 Charging 改；要翻譯就自己在 AssetOps 內翻。為什麼不做 ACL：ChargerFaulted 本來就是業務語言（「設備已聲明自己無法按契約供電」），翻譯沒有價值，只會多一份對照表。

Q5 · ADR-0002 裡 Parking「只做事件契約與 stub」——MVP1 裡誰發 parking.session.closed.v1？誰收？

MVP1 沒有人真的發。contracts/ 裡有它的 JSON Schema 與範例；測試與 E2E 用 stub 發一筆假的（例如 14:33 的 releaseMode=Manual）來驗 Billing 消費者的冪等與合併入口；Billing 收。真正的發布者（既有停車場系統的整合、或我們自己的 Parking context）是 Sprint 2 的事，這件事要寫在 ADR-0002 的「不做清單」與 Day 7 的 sprint-2-backlog.md。

3. WorkOrder 聚合（R5）

  • 識別：workOrderId（WO-2208）。持有 chargerId（CP-A12）與 faultCode（GroundFailure）字串，不持有 Charger 物件。

  readonly chargerId: string;
  readonly faultCode: string;

    this.chargerId = chargerId;
    this.faultCode = faultCode;

    this.openedAt = openedAt;

      chargerId: wo.chargerId,

      faultCode: wo.faultCode,
      occurredAt: input.at,
    });

    return this._status;
  }
  get technicianId(): string | undefined {
    return this._technicianId;
  }
  get outcome(): string | undefined {
    return this._outcome;
  }
  get isOpen(): boolean {
    return this._status !== WorkOrderStatus.Closed;
  }
  get duplicateReportCount(): number {
    return this.reports.length - 1;
  }

      workOrderId: this.workOrderId,
      chargerId: this.chargerId,
      faultCode: this.faultCode,
      occurredAt: at,
    });

    if (!this.isOpen) throw new Error(`Cannot assign: work order ${this.workOrderId} is closed`);
    this._technicianId = technicianId;
    this._status = WorkOrderStatus.Assigned;
    this.record({ type: 'TechnicianAssigned', workOrderId: this.workOrderId, technicianId, occurredAt: at });

    if (!this.isOpen) throw new Error(`Work order ${this.workOrderId} is already closed`);
    this._status = WorkOrderStatus.Closed;

    this.events = [];

  }

  }

Quiz 參考答案

Q1 · ConnectorId 為什麼是值物件不是實體？兩個 ConnectorId.of("CP-A12-2") 相等嗎？

它沒有自己的生命週期與身份——在 Charging 裡我們只在乎「哪一把槍」，不在乎它的歷史（歷史是 AssetOps 的事，那裡它可能是實體）。用值比較、不可變、可以隨意複製。相等：結構相等（starter 用字串所以 === 直接成立），不是參考相等。同一個名詞在不同 context 可以是不同模式。

Q2 · start() 在連接器占用時是拋例外還是記錄 ChargingStartRejected？對明天的 HTTP 回應碼有什麼影響？

記錄事件——R1 原文是「發布 ChargingStartRejected(reason=ConnectorOccupied)，原會話不變」，而且小美要看到被拒的 Start。判準：利害關係人在乎的「不」是事件；呼叫端的 bug（對 Idle 會話 Stop）才是例外。API 端可以同步查回傳的事件回 409 Conflict，或純非同步回 202 Accepted；OCPP ACL 則翻成 idTagInfo.status = 'Blocked'。選擇要寫進 model.md 並在 Day 6 一致。

Q3 · R3：1000 → 7000 → 6500，第三筆之後 lastMeterWh 是多少？接著 stop(13400)，energyWh 是多少？

7000（6500 < 7000 被拒，記錄 MeterValueRejected(NotMonotonic, meterWh=6500, lastMeterWh=7000)，狀態不變）。starter 的 stop() 不帶計量，所以要先 reportMeter(13400)（通過 R3，last=13400）再 stop()：energyWh = 13400 − 1000 = 12400，即 12.4 kWh。教材用的數字是 100 / 4100 / 8100 / 12500，答案同樣是 12400。

Q4 · 為什麼 R5 的「有沒有開放中工單」不能在 WorkOrder 聚合內判斷？那它在哪裡判斷？

需要查其他工單 = I/O；聚合零 I/O，也不該知道其他聚合存在。判斷分兩層：port WorkOrderRepository.findOpenByFault(chargerId, faultCode) 負責查（in-memory 今天、SQLite Day 6），應用層（明天的 FaultProcessManager / ReportFault 處理器）負責決定：有就 appendDuplicateReport(at)，沒有就 WorkOrder.open。聚合只守「開放期間才能附加」。去重鍵 chargerId + faultCode。

Q5 · 聚合的 pendingEvents() / pullEvents() 被誰拉走？拉走之後聚合要做什麼？

應用服務（明天）在命令成功後、同一個交易內拉走，轉成整合事件寫入 Outbox，與聚合狀態一起 commit；relay 之後才發到 bus（R8）。拉走之後聚合要清空——starter 的 pullEvents() 一次做完（回傳並換成空陣列），所以第二次呼叫回 []；R1 測試的第一次 pull 就是在證明這件事。不清空的話，每次 save 都會把舊事件再寫一次進 Outbox，Billing 會收到重複的 ChargingCompleted。

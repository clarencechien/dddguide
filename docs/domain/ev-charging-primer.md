# EV 充電場站入門（給沒碰過充電樁的工程師）

> 對齊 `docs/curriculum.md` §1。本文只講「這個工作坊需要知道的領域知識」，不是充電產業百科。

## 讀完你會拿到

- 能用一句話說清楚 場站（site）/ 樁（charger）/ 槍（connector）三層的差別，以及 kW 與 kWh 為什麼不能混用。
- 能從「車主視角」與「營運視角」各講一遍 14:02 → 18:18 那個午後發生了什麼。
- 知道「三種錢」（停車費、電費、維修成本）各自由誰算、何時算、為什麼不能混在一張單裡算。
- 知道總部（HQ）那一側在乎什麼：資產、健康度、工單、派工、SLA、備品。
- 能解釋「場站在對總部連線中斷時仍要能運作」在工程上到底意味著什麼。

## 1. 一座充電場站長什麼樣

我們的產品假設（curriculum §1.1）：**連鎖停車場營運商**在既有停車場裡新裝充電樁。所以一座場站同時有兩套東西：

```
SITE-TPE-01（場站 site）
├── 閘門 + LPR 車牌辨識（既有停車場系統）
├── 車位（一般車位 / 充電車位 charging bay）
├── 值班室（值班長 阿忠 坐這裡，有一台工作站與一支電話）
└── 充電樁 CP-A12（charger / charge point）
    ├── 連接器 CP-A12-1（connector，俗稱「槍」）
    └── 連接器 CP-A12-2（connector）
```

三個層級一定要分清楚，因為之後每個 Bounded Context 都在其中某一層說話：

| 層級 | 中文 | 英文 | 一句話 | 誰擁有這個詞 |
|---|---|---|---|---|
| 場站 | 場站 | site | 一個有地址、有閘門的地方 | Parking |
| 樁 | 充電樁 | charger / charge point | 一台有韌體、有 OCPP 連線、會壞掉的機器 | AssetOps |
| 槍 | 連接器 | connector | 樁上一個可以獨立插車、獨立計量的出口 | Charging |

**一台樁通常有 1–2 把槍。** 槍才是「賣電的最小單位」：`CP-A12-2` 正在充電時，`CP-A12-1` 仍可服務另一輛車。但樁壞了（例如接地故障）通常兩把槍一起停售，這就是為什麼「故障」掛在樁上、「會話」掛在槍上。

### 1.1 AC 與 DC

| | AC 交流樁 | DC 直流樁 |
|---|---|---|
| 功率 | 7 kW / 11 kW / 22 kW | 50 kW / 120 kW / 180 kW+ |
| 充滿一台 60 kWh 的車 | 約 3–8 小時 | 約 30–60 分鐘 |
| 常見場景 | 停車場、社區、辦公室（**我們的場景**） | 高速公路休息站 |
| 誰在做 AC/DC 轉換 | 車上的車載充電器 | 樁本身 |

工作坊用 AC 樁思考就夠了。停車場的商業模式是「你本來就要停 2 小時，順便充」——這句話會決定很多設計（例如停車費和電費是兩件事）。

### 1.2 kW 與 kWh：最容易搞混的兩個單位

- **kW（千瓦）是功率**：「這把槍現在多快在灌電」。像水龍頭開多大。
- **kWh（千瓦時，俗稱「度」）是能量**：「這次總共灌了多少電」。像水桶裝了多少水。
- 7 kW 的槍充 1 小時 ≈ 7 kWh；充 27 分鐘（14:04 → 14:31）在實務上大約落在 3–7 kWh 之間，但我們範例會話 `S-991` 統一用 **12.4 kWh**（curriculum §1.6），不要為了物理合理性去改它，所有測試、模擬器都對齊這個數字。

**電費按 kWh 算，不按 kW 算。** 所以「度數精度」是帳務的命根子。

### 1.3 計量值（meter value）

樁裡有一顆電表，OCPP 會定期回報「累計讀數」（不是「這段時間用了多少」）。

```
14:04  插槍、授權成功 → 起始讀數 meterStart = 105,200 Wh
14:10  MeterValues     → 106,700 Wh
14:20  MeterValues     → 110,300 Wh
14:31  結束            → meterStop  = 117,600 Wh
                           energyWh  = 117,600 − 105,200 = 12,400 Wh = 12.4 kWh
```

三件事請記住：

1. 讀數以 **Wh 整數** 傳輸（OCPP 慣例），顯示時才轉 kWh。所有事件欄位用 `energyWh`（curriculum §1.8）。
2. 讀數應該**單調遞增**。倒退的讀數代表電表重啟、韌體 bug 或模擬器壞了——這就是規則 **R3**：拒絕並記錄 `MeterValueRejected`。
3. 一次會話的能量 = 最後讀數 − 起始讀數（**R4**），不是把中間所有 MeterValues 加總。

## 2. 一次充電會話：兩種視角

### 2.1 車主視角（車牌 `ABC-1234`，月票憑證 `TAG-MONTHLY-77`）

1. **14:02 進場**：開到閘門，LPR 認出 `ABC-1234` 是月票車，閘門開。停車場系統開了停車會話 `P-441`。
2. 開到充電車位，停好。
3. **14:04 插槍**：把 `CP-A12-2` 的槍插上車。樁螢幕顯示「請刷卡」。刷 `TAG-MONTHLY-77`，螢幕變成「充電中」。
4. 去買咖啡。
5. **14:31**：在 App 上按「停止」或回到車上拔槍。螢幕顯示「本次 12.4 kWh」。
6. **14:33 離場**：開到閘門，閘門開（月票）。過幾天收到一張合併帳單 `INV-778`：停車 0 元（月票）+ 電費 12.4 度。

車主只在乎：**能不能充、充了多少、要付多少、卡住時有沒有人幫我**。

### 2.2 營運視角（值班長 阿忠、充電營運 小美、帳務 老陳）

同一段時間，系統裡發生的**事實**（curriculum §1.7 的黃貼）：

| 時間 | 事實 | 誰在乎 |
|---|---|---|
| 14:02 | `VehicleEntered`（ABC-1234, SITE-TPE-01） | Parking |
| 14:03 | `ChargingBayOccupied` | Parking、Charging |
| 14:04 | `ConnectorPluggedIn`（CP-A12-2） | Charging |
| 14:04 | `ChargingStarted`（S-991, TAG-MONTHLY-77） | Charging、Billing 草稿 |
| 14:10 / 14:20 | `EnergyMetered` | Charging、Billing |
| 14:31 | `ChargingCompleted`（energyWh=12400, stopReason=Local） | Charging、Billing |
| 14:33 | `VehicleExited` | Parking、Billing |

注意每一列的「誰在乎」都不一樣。這是 Day 2 Event Storming 與 Day 3 找邊界的原料。

阿忠會看到的是：值班室看板上 `CP-A12-2` 從「可用」變「充電中」再變「可用」。他**不需要**知道 OCPP、也不需要知道帳單。

小美會看到的是：`S-991` 是月票憑證、在 14:04–14:31 的**尖峰時段**、12.4 度、正常結束（`stopReason=Local`，車主自己停的）。

老陳會看到的是：`P-441` 與 `S-991` 都掛在 `ABC-1234` 底下，可以合併成一張 `INV-778`。

## 3. 費率（tariff）：三種錢與四個坑

curriculum §1.2 說「三種錢」：**停車費、電費、維修成本**。前兩個對顧客收、第三個是公司內部成本。

### 3.1 停車費 vs 電費

| | 停車費 | 電費 |
|---|---|---|
| 計價依據 | 時間（分鐘） | 能量（kWh） |
| 來源事件 | `parking.session.closed.v1`（durationMin） | `charging.session.completed.v1`（energyWh） |
| 誰擁有 | Parking 產生事實，Billing 算錢 | Charging 產生事實，Billing 算錢 |
| 月票車 | 常常 0 元 | **照收**（月票是停車的月票，不是電的） |

**兩張單合併成一張 `INV-778` 是 Billing 的事**，Parking 與 Charging 都不該知道對方的金額。

### 3.2 尖離峰

小美的世界：電力公司對營運商有時間電價，營運商再對車主訂價。範例（工作坊用假數字）：

| 時段 | 電價（元/度） |
|---|---|
| 尖峰 週一至週五 09:00–22:00 | 8 |
| 離峰 其他 | 5 |

`S-991` 全程在尖峰 → 12.4 × 8 = 99.2 元。**跨時段的會話**（例如 21:50 → 22:20）怎麼切？這是 Day 1 訪談小美時要問出來的事，本文故意不給答案。

### 3.3 服務費

有些營運商另收「充電服務費」（每度或每次固定），有些收「占位費」（充完不拔槍、繼續占著充電車位，按分鐘罰）。這些**都是 Billing 的費率規則**，不會改變 Charging 所記錄的事實。

### 3.4 度數精度

- 傳輸與儲存：Wh 整數。
- 顯示：kWh 小數 1–3 位。
- 計價：先算 Wh × 單價 / 1000，最後才四捨五入到「元」。
- 坑：如果 Charging 在事件裡就把 12,400 Wh 四捨五入成 `12.4`，Billing 就永遠拿不回精度。**事件用 `energyWh` 整數是有理由的。**

### 3.5 帳單不可默默改（R7）

`INV-778` 一旦開立，金額不可變。發現尖離峰切錯了，走 `InvoiceAdjusted` 新事件，留下軌跡。老陳的原話：「我不怕錯，我怕改了沒人知道。」

## 4. 總部（HQ）那一側

場站是「賣電的地方」，總部是「讓樁活著的地方」。總部調度 Vicky 與技術員 阿豪 的世界：

| 名詞 | 意思 | 範例 |
|---|---|---|
| 資產（asset） | 每一台樁在總部的登記身份：型號、韌體、裝機日、所在場站 | `CP-A12` @ `SITE-TPE-01` |
| 健康度（health） | 樁最近是否有心跳、故障碼、離線時長 | `CP-A12` 18:10 起 Faulted |
| 工單（work order） | 總部對「一根故障的樁」的承諾：誰、何時、修什麼 | `WO-2208` |
| 派工（dispatch） | 把工單指派給技術員，考慮路線與備品 | `WO-2208` → `TECH-HAO` |
| SLA | 從故障到恢復可售的承諾時間（例如 24 小時） | 18:10 起算 |
| 備品（spare parts） | 修這種故障通常要換的零件，在不在技術員車上 | 接地保護模組 |

Vicky 最常問的問題只有三個：「**哪座樁掛了？誰去修？備品在不在車上？**」阿豪最常抱怨的只有一個：「**工單上寫的樁編號和故障碼對不上現場。**」這兩個人是 AssetOps 與 Dispatch 兩個 context 的代言人。

## 5. 故障生命週期

curriculum §1.2：**申告 → 開單 → 派工 → 修復驗證 → 恢復可售**。

```
18:10  CP-A12 自己回報 Faulted（GroundFailure）        → 申告   ChargerFaulted
18:11  AssetOps 自動開 WO-2208                           → 開單   ops.work_order.opened.v1
18:15  CP-A12 又回報一次同樣的 GroundFailure             → 重複申告，附加到 WO-2208（R5），不開第二張
18:18  Dispatch 指派 TECH-HAO（MVP1 是 stub）            → 派工
（隔天）阿豪到場更換模組、樁回報 Available、Vicky 驗證   → 修復驗證
        WO-2208 關閉                                    → 恢復可售 ops.work_order.closed.v1
```

幾個工程上的重點：

- **申告的主語是設備**。`ChargerFaulted` 的定義（curriculum §1.5）是「設備已聲明自己無法按契約供電」；「App 連不上」的客訴**不是** `ChargerFaulted`，那是另一種東西（可能是網路、可能是 App）。
- **重複申告是常態**：樁可能每 5 分鐘重送一次 `Faulted`，值班長可能同時打電話。R5 保證一根樁一個故障碼在工單開放期間只有一張根因工單。
- **「恢復可售」是 Charging 在乎的結果**，所以 `ops.work_order.closed.v1` 的訂閱者包含「Charging 健康」。但 Charging 從不主動去查工單系統。
- 「現場必須先打電話才產生工單」是 curriculum §1.7 列出的**不該發生的耦合**：這是 Day 1 BPR 要圈出來的「人當 API」。

## 6. 「場站必須在總部斷線時活著」到底是什麼意思

curriculum §1.1 的粗體句：**場站在對總部連線中斷時，仍要能進場、充電、人工放行；對帳可事後補。**

把它翻成工程語言：

| 能力 | 斷線時要能 | 意味著 |
|---|---|---|
| 進場 | 閘門照開 | Parking 的決策在場站本機做，不呼叫總部 API |
| 充電 | 樁照充、計量照記 | OCPP 端點與 Charging 聚合都在場站節點；授權有本機快取或白名單 |
| 人工放行 | 值班長按一下閘門就開 | 規則 R6：發布 `ParkingManuallyReleased`，不等總部 |
| 對帳 | 事後補 | 事件先寫本機 Outbox，連線恢復後再 relay 到總部（R8） |

反過來說，以下設計**會違反**這個要求，Day 3 學員該自己看出來：

- 「Start 充電前先同步呼叫總部驗證憑證」→ 總部掛了整站不能充。
- 「離場閘門要先等 Billing 算完帳單」→ 總部掛了車出不去。
- 「故障要先由總部確認才算故障」→ 現場看板永遠慢半拍。

這就是為什麼 C4 Container 圖（`docs/diagrams/c4-container.mmd`）刻意畫成**兩個節點**：site node 與 HQ node，中間只有事件。

## 7. 那個午後：14:02 → 18:18 敘事版

> 用這段當你 Day 2 Event Storming 的暖身，也是 Day 6 `scripts/e2e` 劇本的原型。

**14:02**，`ABC-1234` 開進 `SITE-TPE-01`。LPR 辨識成功，閘門開，`P-441` 開始計時。阿忠在值班室看板上看到多了一台車。

**14:03**，車停進 3 號充電車位，車位感測器回報占用。看板上的車位變紅——但**這時候還沒有人在充電**，這是 curriculum 特別點名的耦合陷阱：「占用等同充電已開始」是錯的。

**14:04**，車主把 `CP-A12-2` 的槍插上車，樁回報 Preparing。車主刷 `TAG-MONTHLY-77`，樁向場站的 OCPP 端點問「這張卡可以嗎」。場站本機白名單說可以，`S-991` 開始，起始讀數 105,200 Wh。Billing 收到 `charging.session.started.v1` 後開一張草稿。

**14:10、14:20**，兩筆 `EnergyMetered`。Billing 什麼都不做（「每次 MeterValue 都開發票」是另一個陷阱）。

**14:31**，車主在 App 按停止。樁送出結束讀數 117,600 Wh。`ChargingCompleted(energyWh=12400, stopReason=Local)`。Billing 更新草稿：12.4 度 × 尖峰 8 元。

**14:33**，車出閘門。`VehicleExited` → `parking.session.closed.v1(durationMin=31)`。Billing 把 `P-441`（月票 0 元）與 `S-991`（99.2 元）合併成 `INV-778`。

**18:10**，沒有車在充。`CP-A12` 突然回報 `Faulted / GroundFailure`。ACL 把它翻成 `ChargerFaulted(chargerId=CP-A12, faultCode=GroundFailure, stillEnergized=false)`。兩把槍在看板上變灰，停售。

**18:11**，AssetOps 收到 `charging.charger.faulted.v1`，開 `WO-2208`。阿忠**沒有打電話**——這是 To-Be；As-Is 他得打。

**18:15**，`CP-A12` 又送一次一樣的故障。AssetOps 用去重鍵 `chargerId + faultCode` 比對，發現 `WO-2208` 還開著，把這次申告附加上去（R5）。

**18:18**，Dispatch 把 `WO-2208` 指派給 `TECH-HAO`，備品「接地保護模組」標記預留。Vicky 的看板上多了一列。E2E 劇本到這裡結束。

## 自我檢查

1. 樁與槍的差別是什麼？為什麼「會話」掛在槍上、「故障」掛在樁上？
2. `S-991` 的 `energyWh` 是怎麼算出來的？為什麼事件裡用 Wh 整數而不是 kWh 小數？
3. 月票車 `ABC-1234` 的 `INV-778` 為什麼不是 0 元？停車費與電費分別來自哪個整合事件？
4. 18:15 那次重複申告，系統應該做什麼、不該做什麼？哪條規則管這件事？
5. 「場站在總部斷線時仍要能人工放行」對 Parking 與 Billing 的關係有什麼設計上的暗示？

# 講師手冊（Instructor Guide）

> 對象：帶這個工作坊的人。可能是講師、tech lead、或自學者自己扮演講師（那就只讀 §2、§4、§6）。
> 講師的時間投入：Day 1 開場 45 分鐘 + 每天 kickoff 15 分鐘 + 每天驗收 30 分鐘。其餘由主控台與 Claude Code 撐。

## 讀完你會拿到

- Day 1 開場 45 分鐘的逐段腳本。
- Day 2–7 每天 kickoff 15 分鐘的要點卡。
- 學員最常見的十個誤解，以及在哪個時間點用什麼問題攔下來。
- 用主控台投影的方式、驗收交付物的方式。
- 七天砍成五天（或三天）的取捨表。

---

## 1. 講師的角色

你**不是**主要的知識來源——教材與 Claude Code 是。你做三件事：

1. **設定節奏**：kickoff 把今天的「為什麼」講清楚，讓學員知道今天做的東西明天怎麼被用。
2. **攔誤解**：Claude Code 是蘇格拉底式助教，但它看不到學員的表情。你在教室裡走動，聽到「我直接讓 Claude 生一份」就介入。
3. **驗收**：每天 30 分鐘看交付物，用 `docs/rubric.md`。不及格的不是懲罰，是明天 kickoff 的素材。

不要做的事：講 DDD 講 2 小時；Day 1–2 提前講五個 context（curriculum §1.4 明文禁止）；替學員做決定。

## 2. Day 1 開場 45 分鐘腳本

投影 `index.html` Day 1 頁。

### 0:00–0:05 為什麼是這個案子
> 「連鎖停車場新裝充電樁。你們不需要懂充電——如果懂，反而要小心，因為這個工作坊要練的是**從不懂到建模**的過程。七天後你會有一個能跑的 MVP、一套規則的測試、兩份 ADR、一個 PR，以及一份帶回公司的清單。」

畫在白板上：`14:02 進場 → 14:04 插槍 → 14:31 結束 → 14:33 離場 → 18:10 故障`。說：「這一天我們會走七次。」

### 0:05–0:15 七天地圖
逐天一句話（curriculum §2 表）。強調三個轉折：
- Day 2 → 3：從「發生了什麼」到「誰擁有什麼」。
- Day 3 → 4：從圖到程式碼，而且是**測試先**。
- Day 6 → 7：從能跑到能交。

### 0:15–0:25 Claude Code 是什麼樣的助教
現場示範：打 `/ta`，讓大家看它**問問題而不是給答案**。然後示範 `/interview 阿忠`，問一個爛問題（「你需要什麼功能？」）與一個好問題（「上次總部斷線你做了什麼？」），讓大家看回答的差別。

講 20 分鐘規則（`00-orientation.md` §6）。講清楚：**「我卡住 20 分鐘了」是一句有魔力的話，但要誠實**。

### 0:25–0:35 主控台循環
示範一次：按鈕 → 貼 → 對話 → 寫檔 → 勾。強調：
- 主控台不會存進度到雲端，只在瀏覽器。
- 每天結束要 commit 到 `workshop/<name>` 分支。
- 交付物清單就是驗收清單。

### 0:35–0:42 規則與紀律
- 每天三個 Block，做不完用 `/checkout` 補最少的。
- `solutions/` 存在，但看了要重寫。
- 不准兩個語言都做。
- Day 3 之前不准看 curriculum §1.4 與 `docs/domain/glossary.md` §2（可以看 §3 用語衝突——不，也不要）。

### 0:42–0:45 現在開始
「Block 1：45 分鐘內看到一個紅燈、`/ta` 有回應、分支推上去。做完的人開始讀 primer。」

## 3. 每日 kickoff 15 分鐘要點卡

每天固定結構：**昨天驗收的兩個亮點 + 兩個普遍問題（5 分）→ 今天為什麼（5 分）→ 今天的坑（5 分）**。

### Day 2 · Event Storming + 規則
- 昨天：唸兩份好的「人當 API」圈選；指出最常見的引導式問題。
- 為什麼：昨天挖到的事實今天變便利貼；熱點今天變規則。
- 坑：「系統動作當事實」（收到 StatusNotification）；一開始就貼聚合；GWT 沒有數字。
- 一句話：「過去式、有主詞、老陳聽得懂。」

### Day 3 · 戰略設計
- 昨天：唸一條寫得好的 R5 GWT；指出沒有拒絕事件的規則。
- 為什麼：今天決定的邊界，Day 4–6 的目錄就長那樣，改不回來。
- 坑：按技術層切 context；所有關係都畫 Partnership；ADR 後果只寫好處。
- **今天 kickoff 仍然不講五個 context**。下午 Block 2 結束後才對答案。
- 一句話：「同一個字兩群人吵架 = 一條邊界。」

### Day 4 · 戰術 + TDD
- 昨天：投影一張好的 context map；講「答案」與學員版本的差異（通常是四個或六個，都可以）。
- 為什麼：規則要有唯一的家；測試是規格。
- 坑：紅燈是 import error 就開始寫；拒絕用 throw；`Charger` 大聚合；讓 Claude 一次生完。
- 現場示範一個完整的紅綠重構循環（R1 第一個 scenario，10 分鐘），**包括貼失敗訊息給 `/tdd`**。
- 一句話：「沒有紅燈，Claude 不准寫 src。」

### Day 5 · 應用層 + 事件
- 昨天：投影一份聚合的 `pullEvents`；指出誰在聚合裡 `publish`。
- 為什麼：昨天的事件今天要離開聚合；離開的方式決定會不會丟。
- 坑：先 publish 再 save；消費者沒有去重；事件裡放金額；`occurredAt` 用收到時間。
- 白板畫 Outbox 表 + relay 迴圈（`eda.md` §5.2）。
- 一句話：「至少一次 + 冪等，沒有別的組合。」

### Day 6 · MVP
- 昨天：投影一份契約 JSON；指出祈使句事件名。
- 為什麼：今天證明「核心不動、只換 adapter」——如果要改聚合，記下來，那是 retro 素材。
- 坑：ACL 把 OCPP 名詞漏進 domain；`connectorId: 0`；E2E 寫了 15 條；忘記斷線劇本。
- 示範 `scripts/ocpp-sim` 跑一次。
- 一句話：「E2E 一條就好，但要有斷線那一段。」

### Day 7 · SDLC
- 昨天：投影一份 `README-mvp.md`；講誰的 E2E 過了、誰的斷線劇本過了。
- 為什麼：今天把六天變成一個別人能 review 的東西，再變成帶回公司的東西。
- 坑：PR 描述空的；retro 變成檢討人；帶回公司第一件事是「重切 context」。
- 一句話：「reviewer 五分鐘內要知道去哪看什麼。」

## 4. 常見學員誤解與攔截點

| # | 誤解 | 出現時間 | 怎麼攔（用問句） |

| 3 | 「收到 StatusNotification 是事件」 | Day 2 B1 | 「老陳聽得懂這句嗎？」 |

| 5 | 「一個 Session 表加 type 欄最簡單」 | Day 3 B1 | 「人工放行時，那個 Session 的 status 是什麼？」 |
| 6 | 「五個 context 要五個微服務」 | Day 3 B2 | 「MVP1 要幾個程序才能跑 E2E？」 |
| 7 | 「先寫完聚合再補測試比較快」 | Day 4 B2 | 「你的 `ChargingStartRejected` 是怎麼被斷言的？」（通常答不出來，因為他用了 throw） |
| 8 | 「聚合裡直接 publish 省一層」 | Day 4–5 | 「save 失敗的時候 Billing 收到什麼？」 |
| 9 | 「消費者不用去重，broker 保證一次」 | Day 5 B2 | 「老陳上個月那兩張重複帳單是怎麼來的？」 |

| 11 | 「讓 Claude 一次生完整份 storm board / 聚合」 | 全程 | 「Day 3 你要用什麼推導邊界？」「你能解釋第 40 行為什麼在那嗎？」 |

## 5. 用主控台投影

- 投影 `index.html`，字體放到 125%。每個 Block 開始時切到那個 Block，讓大家看到按鈕與交付物。
- 示範時**用你自己的 Claude Code 視窗**，不要用學員的。
- Kickoff 的「昨天亮點」直接投影學員的 `workshop/dayN/` 檔案（事先徵得同意）。
- Day 7 評量頁投影 `docs/rubric.md` 的總表，讓大家自評。
- 主控台可以放到 GitHub Pages（設定 → Pages → main / root），學員手機也能開。連結全部指回 https://github.com/clarencechien/dddguide ，所以不用改任何東西。

## 6. 驗收交付物

每天 30 分鐘，用 `docs/rubric.md` 的當日 DoD。做法：

1. `git fetch --all`，checkout 每位學員的 `workshop/<name>`。
2. 對照 DoD 勾。每份交付物只看**三個地方**（rubric 有標「講師看這裡」）。
3. 記兩個亮點、兩個普遍問題，放進明天 kickoff。
4. 不及格的：`/checkout` 已經告訴他最少要補什麼；你只需要確認他知道。

Day 4–6 的程式碼驗收：`npm test` / `pytest` 綠 + `/aggregate-review` 或 `/event-contract` 無 High + `/review` 抽一個檔案看依賴規則。不要 code review 每一行。

**判斷有沒有抄 solutions**：問他「第 N 行為什麼在那」。答不出來 = 抄了。處理方式：retro 時他自己寫。

## 7. 七天砍成五天 / 三天

### 7.1 五天版（砍什麼）

| 保留 | 砍 | 補償 |
|---|---|---|
| Day 1（訪談 + BPR 合成一天：訪談 3 位、只做故障流程 As-Is / To-Be） | 阿忠與老陳以外的訪談各縮成 5 分鐘 | primer 當回家作業 |
| Day 2 + Day 3 合併：上午 storm + 規則（4 條）、下午邊界 + context map | Example Mapping 只做 R1、R4、R5、R6；C4 只畫 Container；ADR 只做 0001 | ADR-0002 由講師給 |
| Day 4 完整 | — | — |
| Day 5 + Day 6 合併：上午應用層 + Outbox + Billing 消費者；下午 SQLite + E2E | Process Manager 用講師給的骨架；Docker 砍；OCPP 模擬器只跑正常流程 | 故障流程 E2E 用直接發事件代替模擬器 |
| Day 7 縮成半天：`/review` + PR + `/takeaway` | CI、retro 45 分 → 15 分 | CI 範本直接給 |

五天的損失：學員對「故障 → 工單」流程的體感變弱；C4 Context 圖沒畫；沒有 retro 的數字。

### 7.2 三天版（只做核心）

- Day A：primer + 訪談 2 位（小美、Vicky）+ storm 主線與故障支線 + 4 條規則。
- Day B：邊界（講師引導 45 分鐘後直接對答案）+ Day 4 全部（R1–R5 TDD）。
- Day C：應用層 + Outbox + Billing 消費者 + in-memory E2E + `/takeaway`。

三天版不做 BPR、C4、ADR、持久化、HTTP、CI。它是「DDD + TDD + 事件」的濃縮，適合已經有 SDLC 基礎的團隊。

### 7.3 絕對不砍的

1. Day 1 至少兩位訪談（沒有隱藏事實，Day 2 的規則會沒有數字）。
2. Day 3 「自己推邊界再對答案」的順序。
3. Day 4 R1 的完整紅綠重構示範。
4. Day 5 「同一事件送兩次」的測試。
5. 20 分鐘規則。

## 8. 講師自己的準備

- 開課前：自己走一次 Day 1–4（約 1.5 天）。至少讓 R1–R3 綠過一次，你才知道 `/tdd` 會在哪裡卡人。
- 讀完 `docs/domain/stakeholders.md` 的所有隱藏事實——學員會問你「這算不算挖到了」。
- 準備一份你自己公司的「人當 API」例子，Day 1 開場用。
- 開課前一天：確認 `starter/` 兩個語言都能裝、紅燈都在；`scripts/ocpp-sim` 能跑。
- 帶一支計時器。Block 90 分鐘要真的計。

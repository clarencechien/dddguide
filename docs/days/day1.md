# Day 1 — 進場：領域入門、訪談、BPR

**一句話目標**：今天結束時，你能用五位利害關係人的原話描述「一輛車從 14:02 進場到 18:10 樁故障」這個下午，
並且圈出流程裡每一個「人當 API」的交接點，寫出 To-Be 版本。

## 今天結束你會拿到

| 交付物 | 路徑 | 最低要求 |
|---|---|---|
| 訪談紀錄 | `workshop/day1/interviews.md` | 五位角色各一段；每人至少 1 個「隱藏事實」；至少 3 條跨角色矛盾 |
| As-Is 顧客旅程 | `workshop/day1/as-is.md` | 14:02 → 18:10 時間線；圈出 ≥ 4 個「人當 API」交接點 |
| To-Be 流程 | `workshop/day1/to-be.md` | 四原則逐條檢核；保留的人工步驟有理由 |
| 環境 | `workshop/.config`、starter 測試跑過一次 | `/ta` 有正確回應你的 LANG 與 Day |

範本在 `workshop/day1/TEMPLATE.md`；驗收標準在 `docs/rubric.md`。

## 講師開場（45 分鐘版本）

- **[5 分] 這七天在做什麼**：一個真實的複雜領域（充電樁營運）、一條方法論的完整鏈（訪談 → BPR → Event Storming → 戰略 → 戰術 + TDD → EDA → MVP → SDLC）、一個助教（Claude Code）。目標不是學 EV，是學「拿到陌生領域怎麼下手」。
- **[10 分] 領域 60 秒版**（只講這些，其他讓他們自己問出來）：
  - 連鎖停車場新裝充電樁。每站有：既有停車場系統（LPR 車牌辨識、月票、臨停）、新樁（OCPP 1.6J / 2.0.1）、值班室。
  - 總部要看全國樁健康度並派工。顧客三種：臨停、月票、合約車隊。
  - **場站在對總部連線中斷時，仍要能進場、充電、人工放行；對帳可事後補。** 這句話是整個工作坊的地基，寫在白板上一週不要擦。
  - 三種錢：停車費、電費、維修成本。一條故障生命週期：申告 → 開單 → 派工 → 修復驗證 → 恢復可售。
- **[5 分] 五個人**：阿忠（場站值班長）、小美（充電營運）、老陳（帳務）、Vicky（總部調度）、阿豪（技術員）。今天你們會「訪談」他們——由 Claude 扮演，而且每個人都有藏起來不主動講的事。
- **[5 分] 助教怎麼用**：`CLAUDE.md` 讓 Claude 當 TA。規則：它先問你問題；你說「卡住超過 20 分鐘」它才給答案；每次結尾都會有「下一個最小步驟」。教材裡的提示直接貼。
- **[5 分] 今天三個 Block**：B1 環境 + 讀入門；B2 訪談五個人；B3 畫 As-Is、圈「人當 API」、寫 To-Be。
- **[5 分] 什麼是「人當 API」**：舉一個例子就好——「阿忠看到樁面板閃紅燈，打電話給總部，總部人員手 key 一張工單」。這條線裡阿忠的眼睛是 sensor、電話是 transport、總部人員是 deserializer。不用今天就修好，今天只要能**看見**它。
- **[5 分] 交付物與規矩**：三個檔案、放 `workshop/day1/`、commit 到 `workshop/<名字>`。不准抄 `solutions/`（今天也沒東西可抄）。BC 名單今天不講，Day 3 你們自己切。
- **[5 分] Q&A**。講師不要回答「所以有哪幾個系統？」這類問題，回「去問阿忠」。

## Block 1（90 分鐘）— 環境與領域入門

### 目標
repo 跑得起來、Claude Code 認得你、你對這個領域有一張粗略的地圖。

### 步驟
1. Clone 並建分支：
   ```bash
   git clone https://github.com/clarencechien/dddguide.git && cd dddguide
   git checkout -b workshop/<你的名字>
   cp workshop/.config.example workshop/.config   # 編輯：LANG=node 或 LANG=python
   ```
2. 開主控台：直接用瀏覽器開 `index.html`。看一眼七天地圖與今天的按鈕。
3. 跑 starter 測試（這一步會**看到一個紅燈**，那是故意的，Day 4 才會修）：
   - Node：`cd starter/node && npm install && npm test`
   - Python：`cd starter/python && python -m venv .venv && . .venv/bin/activate && pip install -r requirements.txt && pytest`
   把最後 10 行輸出存下來，晚點寫進 check-out。
4. 在 repo 根目錄開 Claude Code，打 `/ta`。確認它說出：你用的 LANG、你在 Day 1、今天三個 Block。如果它不知道，檢查 `workshop/.config` 是否存在。
5. 讀 `docs/domain/ev-charging-primer.md`。邊讀邊在紙上畫：一個場站裡有哪些「東西」（閘門、車位、樁、槍、值班室…）、哪些會「講話」（對誰講）。
6. 寫下 10 個你現在不懂的名詞或問題（例如「idTag 是誰發的？」「一根樁有幾把槍？」）。這張清單是 B2 的訪談彈藥。

### 貼給 Claude Code 的提示
```
/ta

我是 Day 1 Block 1 的學員，剛跑完 starter 測試。這是輸出的最後 10 行：
<貼上>

請不要解釋紅燈怎麼修（那是 Day 4 的事）。我想請你做三件事：
1. 確認你讀到我的 workshop/.config，告訴我你認為我用哪個語言、在第幾天。
2. 我讀完 docs/domain/ev-charging-primer.md 之後列了 10 個不懂的問題（如下）。
   不要直接回答它們。請幫我把這 10 個問題分類：哪幾個應該去問哪一位利害關係人（阿忠 / 小美 / 老陳 / Vicky / 阿豪）？為什麼是那個人？
3. 挑出你覺得我漏問的一個方向，用一個問題提示我（不要給答案）。

我的問題：
<貼上 10 個問題>
```

### 你自己要做的
- 手畫「一個場站」的圖（紙或白板都可以，拍照放進 `workshop/day1/`）。不要讓 Claude 畫，畫錯是今天的重點。
- 決定語言（node / python）。決定了就不要換，Day 4–6 是同一套程式碼一路長大。

### 常見卡點
- **`npm test` / `pytest` 全部失敗而不是「一個紅燈」** → 通常是 Node < 20 或 Python < 3.11。`node -v`、`python --version` 看一下。
- **`/ta` 沒反應或回答很泛** → 你不在 repo 根目錄開 Claude Code，它沒讀到 `CLAUDE.md`。
- **primer 讀不懂 OCPP 那段** → 正常。今天只需要知道「樁會用一種叫 OCPP 的協定對後台講話，訊息名稱像 `StatusNotification`」。Day 6 才會碰它。
- **想先看 `docs/curriculum.md` §1.4 的 context 表** → 別看。看了 Day 3 就沒有東西可推導了。

### 產出
- `workshop/.config` 有 `LANG=`。
- `workshop/day1/` 裡有一張場站手繪圖（`site-sketch.jpg` 或 `.png`）。
- 一份 10 個問題的清單（先放在 `interviews.md` 最上面的「訪談前的問題」小節）。

## Block 2（90 分鐘）— 訪談五位利害關係人

### 目標
從五個人嘴裡挖出：他們每天真正做什麼、最痛的三件事、他們用的詞、以及**他們沒主動說但你問出來的事**。

### 步驟
1. 每位角色 **10 分鐘計時**，順序建議：阿忠 → 小美 → 老陳 → Vicky → 阿豪（從現場往總部走，你會逐漸看到同一件事在不同層的樣子）。
2. 每位角色用一個新的 `/interview <角色>` 對話。開場只准問開放式問題（「你昨天下午做了什麼？」），前 3 分鐘不要問系統。
3. 每個人結束前必問三題：
   - 「有沒有哪件事是你**每天**都要打電話或用 LINE 傳給別人的？」
   - 「跟總部斷線的時候你怎麼辦？」
   - 「這件事如果你講的和 ___（上一位受訪者）講的不一樣，你覺得誰對？」
4. 每問完一位，花 5 分鐘把筆記整理進 `interviews.md`（四小節：一天的工作 / 最痛三件事 / 隱藏事實 / 原話）。**原話**要逐字記——那是 Day 2 glossary 的原料。
5. 五位問完，寫「跨角色矛盾」至少 3 條（例如：小美說「插槍就算開始充電」，老陳說「沒授權的不算」）。
6. 剩下時間回頭再問一位你覺得還有東西沒挖出來的角色。

### 貼給 Claude Code 的提示
```
/interview 阿忠

我是 Day 1 的學員，要訪談你 10 分鐘。請你完全以「場站值班長阿忠」的身份回答，
用他的口吻、他的詞（不要用 DDD 或軟體術語），一次只回答我問的那件事，不要主動列出所有問題的答案。
如果我問得太籠統，請反問我「你想知道哪一種情況？」。
你有一些不會主動講、但被問到會誠實回答的事——請照 docs/domain/stakeholders.md 的腳本守住它們。
訪談結束我會說「謝謝阿忠」，那時請你跳出角色，只告訴我：我「沒問到」的隱藏事實有幾個（不要說內容）。

第一個問題：阿忠，昨天下午 14:00 到 18:30 你在值班室做了哪些事？照時間順序講。
```
換人時把 `阿忠` 換成 `小美` / `老陳` / `Vicky` / `阿豪`，第一個問題改成貼近那個角色的一天：
- 小美：「昨天有幾筆充電是異常中止的？你怎麼知道的？」
- 老陳：「上個月有幾筆帳是客人來爭議的？最常爭什麼？」
- Vicky：「你現在怎麼知道哪座樁掛了？從知道到有人出發要多久？」
- 阿豪：「你到現場之前，工單上會寫哪些東西？哪些是你到了才發現的？」

### 你自己要做的
- 追問。Claude 扮演的角色會等你問；你不問「為什麼」它就不會講「因為總部系統要人工 key」。
- 記原話，不要當場翻譯成術語。「那個槍在閃」就寫「那個槍在閃」。
- 判斷矛盾：兩個人說法不同時，不要急著選邊，記下來。

### 常見卡點
- **角色講得很順、什麼都主動說** → 你的提示沒有要求它「一次只答一題」；重貼上面的提示。
- **10 分鐘問不到隱藏事實** → 換問法：「上次出包是哪一次？」「哪件事你最不想讓總部知道？」「連線斷掉那天你怎麼放人出去？」
- **不知道要問什麼** → 用 B1 的 10 個問題；或用「一天的時間線」逼他講：「14:02 一台車進來，然後呢？」
- **想直接讀 `stakeholders.md` 的隱藏事實** → 可以，但等五位都訪完、`interviews.md` 寫完再讀，然後在檔案裡誠實標出「我沒問到的」。

### 產出
`workshop/day1/interviews.md`，含：
- 訪談前的問題（B1 那 10 個）
- 五位各四小節
- 跨角色矛盾 ≥ 3 條
- 每位「我沒問到的隱藏事實數」（Claude 跳出角色時告訴你的）

## Block 3（90 分鐘）— As-Is / To-Be 與 BPR 四原則

### 目標
把訪談翻成一條時間線（As-Is），圈出「人當 API」的交接點，然後用 BPR 四原則寫 To-Be。

### 步驟
1. **As-Is（40 分）**：用 `docs/curriculum.md` §1.6 的時間軸當骨架——
   `14:02 車牌 ABC-1234 進場 → 14:04 在 CP-A12-2 插槍 → 14:31 充電結束（12.4 kWh）→ 14:33 離場 → 18:10 CP-A12 故障`。
   每一行寫：顧客 / 現場在做什麼、哪個系統、哪個人、是否「人當 API」。填到 `as-is.md` 的表格。
2. 圈出 **≥ 4 個「人當 API」交接點**。判準：一個人在兩個系統之間搬資訊（看螢幕、打電話、手 key、拍照傳 LINE）。每個寫「代價」：等待多久、錯誤率、出錯誰背鍋。
3. 特別寫一段：**連線中斷時 As-Is 會發生什麼**（阿忠 / 老陳 應該有告訴你）。
4. **To-Be（30 分）**：對每個交接點問四原則（`docs/references/bpr.md`）：
   - P1 圍繞結果組織，而非任務
   - P2 資訊在源頭一次捕獲（不再由人抄寫）
   - P3 決策點放在工作發生處
   - P4 以事件連接平行活動，而非事後整合結果
   決定：改（怎麼改）/ 不改（為什麼）。**保留的人工步驟要有理由**（例如：人工放行在斷線時是正確設計，不是待修的 bug）。
5. **（20 分）** 用 `/bpr-review` 檢查。它會挑你沒圈到的交接點與四原則不成立的地方；修完再跑一次。
6. 在 `to-be.md` 末尾列「待驗證的假設」，帶去 Day 2。

### 貼給 Claude Code 的提示
```
/bpr-review

這是我的 workshop/day1/as-is.md 與 workshop/day1/to-be.md（請直接讀檔）。
請不要重寫它們。請做：
1. 逐一檢查我圈的「人當 API」交接點：每個交接點問我一個問題，讓我確認它真的是「人在兩個系統之間搬資訊」，而不是「人在做判斷」。
2. 你認為我漏掉的交接點：只告訴我「在時間線的哪一段」，不要告訴我是什麼。
3. To-Be 的四原則：挑出你覺得站不住的一條，問我「如果連線中斷，這條還成立嗎？」
4. 最後給我「下一個最小步驟」。
```

### 你自己要做的
- 決定哪些人工步驟**要留**。這是判斷題，Claude 不能替你決定；它只能問你「留下來的理由是什麼」。
- 把「連線中斷」當成第一公民，不是例外情境。To-Be 每一行都問一次「斷線時這行還走得通嗎？」。

### 常見卡點
- **As-Is 寫成系統功能清單而不是時間線** → 回到 14:02。每一行開頭要有時間。
- **交接點圈不到 4 個** → 看故障那段（18:10 之後）：誰看到、誰通知、誰開單、誰派人、誰確認修好、誰把樁重新上架。
- **To-Be 把所有人工步驟都自動化了** → 想想 §1.1 那句話：「連線中斷時仍要能……人工放行」。全自動的 To-Be 在斷線時會把顧客關在場內。
- **四原則不知道怎麼套** → 一個交接點套一條就夠；不必每個交接點四條全套。

### 產出
- `workshop/day1/as-is.md`：時間線表、≥ 4 個交接點與代價（含「如果他請假」）、增值時間與總時長、斷線情境。
- `workshop/day1/to-be.md`：To-Be 表、四原則逐條（標 P1–P4）、保留的人工步驟、改動後產生的事實清單（過去式，≥ 8）、「故意沒有的東西」段、待驗證假設。
- `/bpr-review` 第二次跑的結果沒有新的「漏掉的交接點」。

## Check-out（30 分鐘）

### Quiz（5 題）
1. 「連接器（Connector）」和「一根樁」是同一個東西嗎？`CP-A12-2` 的 `-2` 是什麼？
2. 阿忠說「插槍了」和小美說「開始充電了」，在 As-Is 裡是同一個時間點嗎？
3. 舉一個你今天圈出的「人當 API」交接點，用一句話說它為什麼是（sensor / transport / deserializer 分別是誰）。
4. 連線中斷時，阿忠現在（As-Is）怎麼放車出場？你的 To-Be 保留了這條嗎？為什麼？
5. BPR 四原則裡的 P2「資訊在源頭一次捕獲」套在故障申告上，會把哪個人從流程裡拿掉？拿掉後誰知道樁壞了？

<details>
<summary>參考答案</summary>

1. 不是。樁（Charger，`CP-A12`）是一台設備，可以有多把槍；連接器（`CP-A12-2`）是第 2 把槍的**業務身份**。之後 Charging 的不變條件會掛在連接器上，不是樁上。
2. 不是。插槍（T2 `ConnectorPluggedIn`）和授權開始（T3 `ChargingStarted`）是兩個事實，中間隔著授權（憑證 `TAG-MONTHLY-77` 有沒有效）。把兩者混為一談是 §1.7 列的「不該發生的耦合」。
3. 例：18:10 樁面板閃紅 → 阿忠看到（sensor）→ 打電話（transport）→ 總部人員聽完手 key 工單（deserializer）。代價：延遲、聽錯樁編號、下班後沒人看面板。
4. As-Is：阿忠手動抬桿，事後用紙本或 LINE 補給老陳對帳。To-Be 應該**保留**人工放行，但把它變成一個被記錄的事實（之後會叫 `ParkingManuallyReleased`），讓帳務事後對齊，而不是靠紙條。
5. 拿掉「打電話的阿忠」與「手 key 的總部人員」：樁自己申告（之後是 `ChargerFaulted`），總部系統自己開單。阿忠仍然會知道——他訂閱看板，但不再是傳輸層。
</details>

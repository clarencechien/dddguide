## 講師開場（15 分鐘）

- **[3 分] 昨天的收穫回收**：請 2 位學員各念一句訪談原話。指出：那些原話今天要變成「事實」和「詞」。
- **[4 分] Event Storming 只有一條規則**：黃貼只貼**已發生的事實，過去式**。「系統送出 StatusNotification」不是事實，「充電器已申告故障」才是。「使用者按下開始」也不是事實，「充電已授權開始」才是。事實是業務會在乎的、發生了就不能收回的東西。
- **[3 分] 三個層次**：早上 big picture（只貼事實）→ 加命令 / 政策 / 聚合候選 / 角色（process-level）→ 下午把規則寫成例子（Example Mapping）。今天不畫邊界，邊界是明天的事。
- **[2 分] 數字例子**：每條規則至少一個成功例、一個拒絕例，用 `S-991`、`CP-A12-2`、`12.4 kWh`、`TAG-MONTHLY-77` 這組識別碼。抽象規則寫不出測試。
- **[2 分] 助教今天的角色**：`/storm` 會糾正你「系統動作當事實」；`/rules-check` 會挑 GWT 少了什麼。它們不會替你貼便利貼。
- **[1 分] 交付物**：三個檔案，放 `workshop/day2/`。

## Block 1（90 分鐘）— Big-picture Event Storming

### 目標
把 14:02 → 18:10 這個下午鋪成一條只有「事實」的時間線，加上故障支線，標出爭議點（hotspots）。

### 步驟
1. **（20 分，不開 Claude）** 拿便利貼或空白文件，從訪談原話裡抓事實。每張一句，過去式，主詞是業務物件不是系統：
   「車輛已辨識進場」「連接器已插上」「充電已授權開始」「電量已計量」「充電已結束」「車輛已離場」「充電器已申告故障」。
   先貼再排序，貼滿 20 張以上再說。
2. 依時間排成主線。每張標「誰在乎」（從訪談來：阿忠在乎進場、小美在乎授權、老陳在乎結束…）。
3. 拉出**故障支線**：18:10 之後發生了什麼事實？（申告 → 開單 → 派工 → 修復驗證 → 恢復可售，每一步都是一個事實。）
4. **hotspots（紅貼）**：兩個人說法不一樣的地方（Day 1 的矛盾清單）、你不確定的地方、外部系統（LPR、OCPP、發票系統）。
5. **（50 分）** 開 `/storm`，把你的初稿貼給它。它會挑出「不是事實的事實」；每被挑一張你就改一張，改的理由寫在旁邊。
6. **（20 分）** 整理進 `storm-board.md`：主時間線表 + 故障支線表 + hotspots 清單 + Mermaid `timeline`。

### 貼給 Claude Code 的提示
```
/storm

我是 Day 2 Block 1，做 big-picture Event Storming。這是我的第一版事實清單（每行一張黃貼，含時間與「誰在乎」）：
<貼上>

請你當 facilitator，不要當作者：
1. 逐張檢查是不是「已發生、過去式、業務會在乎的事實」。不是的話不要幫我改寫，只問我一個問題讓我自己改（例如「這是系統做的動作還是業務上發生的事？」）。
2. 指出時間線上「兩張貼紙之間應該還有一個事實」的縫隙——只說「在 X 和 Y 之間」，不說是什麼。
3. 故障支線：我貼了幾張？從「申告」到「恢復可售」你認為缺了幾個事實（只說數量）？
4. 幫我把「hotspot」和「事實」分開：哪幾張其實是爭議而不是事實？
最後給我「下一個最小步驟」。
```

### 你自己要做的
- 決定每個事實的**名字**（中文 + 英文）。Claude 會挑毛病但不該替你命名；命名是通用語言的起點。
- 決定哪些事實你**不確定**——誠實貼紅貼，比硬湊一條完整時間線有價值。

### 常見卡點
- **貼出來的都是系統動作**（「系統寫入資料庫」「後台送 StatusNotification」）→ 問自己：小美或老陳會在乎這件事嗎？他們在乎的是「充電已結束、12.4 kWh」，不是哪個 API 被呼叫。
- **貼出來的是狀態**（「連接器是 Occupied」）→ 狀態是事實的結果；改成事實：「連接器已被占用」。
- **時間線太短（< 10 張）** → 把「充電已結束」到「車輛已離場」之間拆開：帳單什麼時候產生？停車費什麼時候算？月票車主和臨停車主一樣嗎？
- **故障支線不知道怎麼開始** → 回去看阿豪和 Vicky 的訪談：「你怎麼知道樁壞了？」的答案就是第一張。
- **想把「連線中斷」貼成事實** → 它可以是事實（「與總部連線已中斷」），但更重要的是它旁邊那張：「值班長已人工放行」。

### 產出
`workshop/day2/storm-board.md` 的前半：主時間線表（≥ 7 張）、故障支線表（≥ 5 張）、hotspots（≥ 4 個）、Mermaid timeline。

## Block 2（90 分鐘）— Process-level：命令、政策、聚合候選、角色

### 目標
在每個事實前面放「是什麼命令觸發它」、「誰下的命令」、「發生後自動接什麼政策」，然後從動詞的受詞裡浮出聚合候選，標出樞紐事件。

### 步驟
1. **（15 分，不開 Claude）** 對主線每張事實，補三欄：
   - 命令（Command，祈使句）：`StartCharging`、`StopCharging`、`ReportMeterValue`、`ReportFault`、`ReleaseVehicle`…
   - 執行者（Actor）：顧客、阿忠、樁（設備也可以是 actor）、時間（timer）。
   - 政策（Policy，「每當 X 就 Y」）：「每當充電已結束，就建立草稿帳單」「每當充電器已申告故障，就開工單」。
2. **拒絕事件**：命令會失敗。每個命令旁邊寫「失敗時發生什麼事實」：`ChargingStartRejected`、`MeterValueRejected`。這些明天後天都會用到。
3. **聚合候選**：把命令的受詞圈起來——「開始**充電會話**」「開**工單**」「開立**帳單**」「放行**停車會話**」。受詞就是候選；一個候選要能回答「哪些命令打在我身上、我守什麼規則」。
4. **樞紐事件（pivotal events）**：時間線上畫垂直線的地方——線的兩邊「在乎的人」明顯換了一批。通常是 `ChargingStarted`、`ChargingCompleted`、`VehicleExited`、`ChargerFaulted`。這些線明天會變成邊界的線索，**但今天不要說「這是 context」**。
5. **（45 分）** 再開一輪 `/storm`，這次針對命令 / 政策 / 聚合候選。特別問它：哪個政策你寫成了「同步呼叫」（例如「充電結束時呼叫總部工單 API」），其實應該是事件驅動。
6. **（30 分）** 把 glossary 起稿：從時間線的名詞抓出 ≥ 12 個詞，每個寫「是 / 不是」。「不是」那欄要填 Day 1 訪談裡容易混淆的東西（`ChargingSession` 不是 OCPP Transaction；`Invoice` 不是 MeterValue 陣列）。

### 貼給 Claude Code 的提示
```
/storm process

Day 2 Block 2，process-level。這是我補了命令 / 執行者 / 政策 / 拒絕事件的時間線，以及我圈出的聚合候選與樞紐事件：
<貼上 storm-board.md 目前內容>

請：
1. 對每個政策問我：「這是『每當 X 就 Y』，還是你其實寫了一個同步呼叫？如果 Y 那邊的系統掛了，X 會失敗嗎？」
2. 對每個聚合候選問我：「哪些命令打在它身上？它要守住的一條規則是什麼？」——我答不出來的候選你就標成「待定」。
3. 對每個樞紐事件問我：「線的左邊和右邊，在乎的人各是誰？」
4. 我的 glossary 草稿在下面。挑出 3 個「是 / 不是」寫得太籠統的，各問我一個具體情境讓我改。
不要幫我補完表格；不要提 Bounded Context 這個詞（明天才做）。最後給「下一個最小步驟」。

glossary 草稿：
<貼上>
```

### 你自己要做的
- 命令的命名：動詞 + 受詞，祈使句，英文。你決定叫 `StartCharging` 還是 `BeginSession`——選一個，全隊（就是你）一路用到 Day 6。
- 決定哪些詞**不要用**。訪談裡的「交易」「transaction」「那個槍」都要決定改用什麼。

### 常見卡點
- **政策寫成同步呼叫** → 看 §1.7 最後一欄「不該發生的耦合」：每一行都是一個反例。
- **聚合候選太大**（「場站」「充電系統」）→ 問「一個命令會同時改到幾個它？」如果 `StartCharging` 只改一個連接器上的一個會話，候選就是會話，不是場站。
- **聚合候選太小**（「MeterValue」）→ 問「它自己守得住什麼規則？」單一計量值守不住「單調遞增」，會話才守得住。
- **glossary 的「不是」欄寫不出來** → 從 Day 1 矛盾清單抄：兩個人講不一樣的那個詞，就是「不是」欄要寫的東西。

### 產出
- `workshop/day2/storm-board.md` 完整：時間線含命令 / 執行者 / 政策 / 拒絕事件、聚合候選（≥ 3 個，每個有「守的規則」）、樞紐事件（≥ 3 個）。
- `workshop/day2/glossary.md` 初稿：≥ 12 個詞、≥ 3 個「不要用的詞」。

## Block 3（90 分鐘）— Example Mapping：把規則寫成 Given/When/Then

### 目標
從 R1–R8 選至少 6 條，每條寫成可以直接變測試的 GWT，帶數字例子，有成功也有拒絕。

### 步驟
1. 讀 `docs/curriculum.md` §1.9 的 R1–R8。這八條是課程給的「規則卡」（藍卡）；你今天的工作是替每條卡配「例子卡」（綠卡）和「問題卡」（紅卡）。
2. **（30 分，不開 Claude）** 每條規則寫：
   - Context（哪條時間線 / 哪個聚合候選守它）
   - 命令
   - 成功事件 / 拒絕事件
   - ≥ 2 個例子（一成功一拒絕），Given/When/Then 三段，**每段都有數字或識別碼**。
   例（R1）：
   ```
   Given 連接器 CP-A12-2 上有進行中的充電會話 S-991（14:04 開始，憑證 TAG-MONTHLY-77）
   When  14:10 另一張憑證 TAG-VISITOR-03 對 CP-A12-2 下 StartCharging
   Then  發布 ChargingStartRejected(connectorId=CP-A12-2, reason=ConnectorOccupied)
         且 S-991 狀態不變、起始計量不變
   ```
3. R3 一定要寫**邊界例子**：計量值相等算不算倒退？（決定並寫下來。）R4 一定要有**數字**：起始 1000 Wh、最後 13400 Wh → `energyWh = 12400`。
4. R5 的例子要有「工單開放期間」的時間：18:10 第一次申告 `E42` → 開 `WO-2208`；18:15 再申告 `E42` → 不開新單、`WO-2208` 附加「重複申告」；18:15 申告 `E17` → 開新單。
5. R6、R7、R8 不一定要寫成測試（MVP1 不實作 Parking 與 Billing 完整版），但至少各寫一個例子，因為 Day 3 切邊界要用。
6. **（40 分）** 用 `/rules-check` 驗收。它會逐條挑：缺 context？缺拒絕事件？例子沒數字？改完再跑。
7. **（20 分）** 把每條規則寫的「問題卡」（你不確定的地方）收進 `rules.md` 末尾的「待決問題」。

### 貼給 Claude Code 的提示
```
/rules-check

Day 2 Block 3。這是我的 workshop/day2/rules.md（請直接讀檔）。
請逐條檢查每條規則有沒有：context、命令、成功事件、拒絕事件、至少一個成功例與一個拒絕例、每個例子都有數字或識別碼。
輸出格式：每條規則一行「Rn：缺 ___」或「Rn：完整」。
缺的部分不要幫我補；每個缺項給我一個「你會怎麼回答這個情境」的問題。
另外挑一條你認為「Then」寫得像實作細節（例如提到資料庫或 API）而不是事實的，告訴我是哪條，不告訴我怎麼改。
最後給「下一個最小步驟」。
```

### 你自己要做的
- 數字。所有數字。Claude 不該替你決定起始計量是 1000 還是 0。
- R3 的「相等算不算倒退」——你決定，寫進 rules.md，Day 4 的測試會照這個寫。
- R4 的 `energyWh` 用 Wh 還是 kWh 存？（提示：§1.8 契約用 `energyWh`。）

### 常見卡點
- **Then 寫成「資料庫更新為 Charging」** → Then 是事實：「發布 `ChargingStarted(sessionId=S-991, connectorId=CP-A12-2, idTag=TAG-MONTHLY-77, startedAt=14:04)`」。
- **拒絕例寫不出來** → 每條規則的動詞前面加「不能」：不能在占用時開始、不能未授權開始、不能倒退計量、不能在非 Charging 時 Stop、不能重複開單。
- **例子沒數字** → 強迫自己用 §1.6 那組識別碼與 §1.6 的時間軸。
- **6 條寫不完** → 先寫 R1–R4（明天後天一定會用），R5 一條，R8 一條。

## Check-out（30 分鐘）

### Quiz（5 題）
1. 「後台收到 `StatusNotification(Faulted)`」為什麼不能當黃貼？正確的黃貼是什麼？
2. `ChargingBayOccupied`（T1）和 `ChargingStarted`（T3）之間隔了什麼事實？把它們合併成一張會犯 §1.7 的哪個耦合？
3. 「每當充電已結束，就呼叫總部工單 API 建單」——這是政策還是同步呼叫？如果總部掛了，充電還能結束嗎？
4. R4 的例子：起始計量 1000 Wh、最後計量 13400 Wh，`ChargingCompleted.energyWh` 是多少？如果最後計量是 900 Wh 呢（R3）？
5. 你的聚合候選裡，哪一個守 R1？它需要知道「這根樁的韌體版本」嗎？

<details>
<summary>參考答案</summary>

1. 那是系統動作（訊息傳輸），不是業務事實；而且用了 OCPP 的詞。正確的是「充電器已申告故障 `ChargerFaulted`」——設備已聲明自己無法按契約供電。
2. `ConnectorPluggedIn`（T2）與授權。合併會犯「占用等同充電已開始」與「插槍等同已授權扣款」。
3. 寫法是同步呼叫。應改為政策：「每當 `ChargingCompleted` 就…」由事件驅動，總部掛了充電照樣結束、事件留在 Outbox 稍後送出（R8）。
4. 12400。900 Wh 是倒退，依 R3 拒絕並記錄 `MeterValueRejected`，會話的最後計量維持原值；不會產生 `ChargingCompleted`。
5. 充電會話（`ChargingSession`）——它知道自己在哪個連接器、狀態是否進行中。它**不需要**韌體版本；那是另一群人（Vicky、阿豪）在乎的資產資訊，塞進來會讓聚合變胖、把不同生命週期綁在一起。
</details>
